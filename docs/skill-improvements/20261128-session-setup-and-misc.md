# セッションの立ち上がりと周辺の改善点（2026-11-28）

コーヒーショップのセッション（`eventstorming-20261128-1105`）の序盤から終盤で出た改善点のうち、他のメモに入っていなかったものを追記する。末尾に、同日の全メモの一覧を付ける。

## 1. 最初の `dmlctl init` が、依存ライブラリ不足で失敗した（優先度 高）

- ○ クラウドのセッションで最初に `dmlctl init` を実行したところ、終了コード 3 で失敗した。「set/add/remove/update/init/rename には ruamel.yaml が必要です（`pip install ruamel.yaml`）」。
- その場で `pip install ruamel.yaml pyyaml jsonschema` を実行して先へ進んだ。root での pip 警告も出た。
- CLAUDE.md には「Python 3 と `pyyaml` / `jsonschema` / `ruamel.yaml` が必要」とあるが、**クラウドの新しいセッションには入っていない**。最初の 1 ターンが、依存の解消に取られる。
- 提案:
  - リポジトリに SessionStart フック（この環境にある `session-start-hook` スキルの用途）を置き、セッション開始時に依存をインストールする。
  - `requirements.txt` をスキルの下に置き、SKILL.md の冒頭に `pip install -r` を 1 行書く。
  - `dmlctl` が依存不足で落ちるときの案内に、インストールのコマンドをそのまま載せる（今も載っている。この点は良い）。
- 「最初のターンで Artifact を公開する」（`20261128-artifact-first-publish.md`）を実現するために、この依存の解消が先に要る。

## 2. Artifact の通知コメントが、スレッドにたまる（優先度 中）

- ○ 回答のたびに、パネルが同じスレッドにコメント（「【グリル回答】回答が届きました…」）を足す。スレッドを読むと、そのほとんどが「awaiting reply（返信待ち）」の印のまま並んでいた。
- SKILL.md の手順 6 は、「コメントで起きたら、そのスレッドに返信する」と書く。ただし、回答が連続すると、毎回の返信は手間で、返信しても読み手にとっての価値が低い。実際は、数回に 1 回しか返信しなかった。
- 提案:
  - 返信は、確認の質問を出した（食い違いがある）ときだけに絞る。通常の反映は、反映エリアの `summary` で伝わる。
  - パネルは、通知コメントを 1 本に畳む（回答のたびに別のコメントを足さない）。

## 3. 通知が、処理済みの回答に対しても届く（優先度 中）

- ○ 通知（Webhook）は、回答のたびに届く。処理済みの回答に対する通知が、あとから届くことがあった（通知の版が、すでに再公開した版を指す）。
- そのたびに、`ReadNotifications` と `answers` の確認で 2〜3 回のツール呼び出しが要る。確認の結果、新しい回答がないことも多かった。
- 提案: 通知を読んだら、`answers` を 1 回だけ見て、`reflected` に無い qid がなければ、チャットでは何も言わずに終える、と SKILL.md に書く。

## 4. DML の直接参照を止めるフックが、Grep ツールと Bash には効かない（優先度 低）

- ○ CLAUDE.md は「`docs/eventstorming/*.dml.yaml` への Read/Edit/Write はフックが止める」と言う。実際は、`Grep` ツールで DML の中身の行が返ってきた（「キャラ」を探したとき）。Bash の `grep -c` も通った。一方、Bash で Python を使って DML を読もうとしたときは、自動モードの権限チェックが止めた（これはフックではなく、環境の仕組み）。
- 私は、語の残りを探す目的で `Grep` を使った。方針の趣旨（AI が全文を読み込まない・直接編集しない）には反さない使い方だが、フックが守っているのは Read/Edit/Write だけ、という実態は、方針の説明から読み取れない。
- 提案: 「直接の `Edit`/`Write` は止める。`Grep`・Bash の読み取りは、語の探索に限って許す」と、CLAUDE.md に書く。あるいは、`dmlctl refs` を使うよう案内する（識別子の探索に使える）。散文中の語は、`dmlctl refs` に出ないため、探索の手段が要る（`dmlctl grep` のような読み取り専用の探索）。

## 5. 最初の発言がドメイン名だけのとき、どのスキルを使うかの確認がない（優先度 低）

- ○ 最初の発言は「コーヒーショップ」だけだった。スキルは 2 つある（EventStorming／DDD、ディメンショナル・モデリング）。私は、確認せず EventStorming を選び、チャットで 1 行「EventStorming（DDD）のファシリテーターで進めます」と伝えた。
- 結果としては、オーナーが EventStorming を望んでいたので、支障はなかった。
- 提案: どちらも当てはまりそうなときは、最初のターンで 1 行、「運用の流れを整理する（EventStorming）」か「数字で測る分析モデル（ディメンショナル）」かを聞くか、選んだ理由と切り替え方を添える。Artifact の最初の質問（最初のターンに公開）に、この選択肢を 1 問目として載せてもよい。

## 6. データベースを使うページは、ギャラリーのサムネイルが付かない（優先度 低）

- ○ 公開結果に「データベースを使うページは、自動のスクリーンショットが付かない」と出た。ギャラリーのカードは、画像なしになる。
- 提案: `--artifact` ビルドで、サムネイル用の小さな画像（セッション名とフェーズの帯など）を出して、`<link rel="artifact-thumbnail">` で付ける。優先度は低い。

## 7. 「反映中」の表示が回り続けた（優先度 中）

- ○ オーナーから「アーティファクトは反映中の回転のまま変わらない」と指摘があった。調べると、回答 46 件のうち、反映済みの記録（`grill/progress.reflected`）に無いのは 1 件（質問 q-20261128-47）だけだった。その回答は、私が前のターンを終えた直後に届いていて、処理されないままだった。パネルは「未反映の回答が 1 件ある」ために、回転を出し続けた。
- 仕組み上は、回答が届くと通知で私のセッションが起きる。ただし、起きるまでの間（ターンの切れ目）は、画面から見ると「反映中」のまま、いつまで続くのか分からない。
- 提案:
  - パネルは、反映待ちの回答に**届いた時刻と経過時間**を出す。5 分を超えたら、「Claude が起きていないかもしれません。進行役に『回答した』と伝えてください」と案内する（「制約」の節にある案内の、時間版）。
  - Claude 側は、ターンを終える前に、必ず `answers` を読み直し、未反映がないことを確かめる（SKILL.md の手順 7 は書いてあるが、実行が抜けやすい）。確かめ方を、1 コマンドの手順にする（`answers` の qid と `reflected` の差を出す小さなスクリプト）。
  - 「全部反映済み」のときは、パネルの回転を止め、「すべて反映済み」と出す（今も出る）。
