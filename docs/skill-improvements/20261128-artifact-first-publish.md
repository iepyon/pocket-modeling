# Artifact を最初から作り、質問も Artifact に出す（2026-11-28）

コーヒーショップのセッション（`eventstorming-20261128-1105`）で、オーナーから出た指摘。
「なかなかアーティファクトつくらないね？」「すぐアーティファクト作って、アーティファクトで質問」。

## 何が起きたか

- ユーザーの最初の発言は「コーヒーショップ」だけ。
- 実際の進み方は次のとおり。
  1. フェーズ 1（スコープ確認）の質問 3 問を、**チャット**で出した（店の種類、目的、AI エージェントの置き場所）。
  2. `dmlctl init` でセッションを作り、ハッピーパスの散文をチャットで聞いた。
  3. 代替シナリオの質問も、チャットで出した。
  4. ここでオーナーから「なかなか作らないね」と言われた。**Artifact を初めて公開したのは、その後**。
- Artifact を公開したのは、ユーザーのやり取りが 5 往復したあと。それまでの質問は、すべてチャット内にあった。

## 原因

### 1. 手順の書き方が、チャット前提の順になっている

- SKILL.md のワークフロー表は、フェーズ 1 の書き出しを「`session`（実書き込みはフェーズ 2 冒頭の `dmlctl init`）」としている。**フェーズ 1 では HTML を作らない**と明記している。
- 「Artifact 上のグリル」の節は、ファイルの**末尾近く**にある。「③ HTML 出力」の 1 行に「Artifact ツールがあるセッションでは Artifact が既定」とあるだけで、フェーズ 1 の質問を Artifact に出せとは読めない。
- フェーズ 2 の完了で「`Bash open` で HTML を初回起動」とある。Artifact のセッションでも、まずこの手順を踏むように読める。

### 2. 「最初の質問」を出すには、DML と Artifact が先に要る

- 質問パネルは、Artifact の db（`grill/current`）から質問を読む。Artifact を公開しないと、フェーズ 1 の質問は載せられない。
- 手順が「質問で範囲を決めてから DML を作る」順なので、最初の数問は、構造上チャットに出るしかなかった。

### 3. 空の DML でも公開できるのに、その前提で書かれていない

- 確認済み: `dmlctl init` 直後の、シナリオが 1 本もない DML でも、`eventstorming_build.py <dml> --artifact` は成功する（約 73KB の HTML ができる）。
- つまり「内容が揃ってから公開」にする技術的な理由はない。

## 提案

### A. 最初のターンで、init → 公開 → 質問をパネルへ（優先度 高）

`Artifact` ツールがあるセッションでは、ユーザーの最初の発言を受けたら、**質問をチャットに出す前に**次を行う。

1. `dmlctl init` で DML を作る。`--domain` には、最初の発言をそのまま入れる（例: コーヒーショップ）。`--goal` は後で `set` する。
2. `eventstorming_build.py <dml> --artifact` → `Artifact` で公開（`capabilities` は SKILL.md のとおり）。
3. `grill/current` に、フェーズ 1 の質問を 2〜3 問積む（店の種類、目的、AI エージェントの置き場、など）。
4. チャットには、URL を 1 行と、「質問はページ上部に出しています」だけを出す。**質問文そのものはチャットに載せない**。

### B. 質問は Artifact だけに出す（優先度 高）

- フェーズ内往復の質問をチャットに再掲しない。このセッションでは、質問をチャットの本文と質問パネルの両方に書いた場面があり、回答先がどちらか迷いやすかった。
- チャットは、「何を反映したか」「何が決まったか」「次に何が出るか」の差分報告と、確認が要る食い違いの報告に絞る。
- チャットで答えてもらう必要がある場合（Artifact が開けない人）にだけ、チャットにも質問を出す。

### C. SKILL.md の構成（優先度 中）

- 「Artifact 上のグリル」の概要 3 行を、**ファイルの先頭近く**（9 フェーズの表より前）に移し、「Artifact ツールがあれば、最初のターンに init して公開する」を最初の指示にする。
- フェーズ表の「1. スコープ確認」の書き出しを、「`session`（`dmlctl init` を最初のターンで行い、`goal` などは `set` で埋める）」に直す。
- フェーズ 2・3 の「`Bash open` で HTML を開く」は、Artifact のセッションでは「Artifact を再公開する」に読み替える、と明記する。

### D. 周辺の小さな摩擦（優先度 低）

- 質問が尽きたとき、`grill/current` が空になると、パネルが「次の質問を用意しています」と出す。回答を待たせない規則（常に 2〜3 問先まで積む）は書いてあるが、初回の積み方の例がない。フェーズ 1 の質問 3 問の例を、SKILL.md に載せる。
- 質問の選択肢を直す（誤字など）と、回答済みの質問は出し直せない。**別メモ**（`20261128-grill-panel-reselect-answers.md`）に分けた。

## 受け入れ条件

- ユーザーの最初の発言から、1 往復以内に、Artifact の URL と最初の質問がパネルに出る。
- フェーズ 1 の質問が、チャットには出ない。
- 空の DML で公開した Artifact が、「質問に答えると、ここにモデルが育ちます」という空の状態を、きちんと見せる。

## コスト

小。技術的な変更はほぼ要らない（空の DML のビルドは動く）。SKILL.md の構成の入れ替えと、フェーズ 1 の質問の例の追記が中心。空の状態の見せ方（HTML 側）は、実際のページを見て調整する。
